# 我把 1.75 GB 工作資料交給 AI agent 刪掉了：一次路徑未正規化的資料損失與檢討

> 2026-11-16，我在自己的 Windows 11 桌機上，讓一個桌面 AI agent（DSH，full access 模式）幫我測試自製的卸載腳本。腳本的路徑防護有一個自相抵銷的缺陷，`-Dest "C:\"` 通過了所有檢查，接著執行 `cmd /c rd /s /q "C:\"`，把工作資料夾整棵樹刪掉——1,372 個檔案、143 個目錄、約 1.75 GB。**檔案清單與大小靠 Windows VSS 影子複本救回，但有一部分內容是零。**
>
> 這篇是去識別化的完整檢討：時間線、根因、為什麼快照「看起來」救了這件事、以及任何在用 AI agent 的人可以照做的防護步驟。本文不含主機名稱、使用者名稱或任何私人專案內容。

> ### 2026-11-18 更正：初版有三個結論是錯的
>
> 1. **「完整救回」不成立。** 影子的檔案大小正確、但內容有整段是 NULL。復盤後確認 78 個以上檔案有零段、15 個全毀。這與 Windows 已知的 VSS NULL 區塊行為高度吻合，但 261116 是否由它造成仍未證實，見 [`vss-null-blocks.md`](vss-null-blocks.md)。
> 2. **「刪除約 2–3 分鐘」不準確。** 實際是 19:02:16 送出、19:04:23 被中止，上限 127 秒；發現時間是 19:05:25，不是 19:07。
> 3. **根因不是「`USERPROFILE` 比較永遠不成立」。** 那道檢查有效，測試時確實擋下了。失效的是磁碟根檢查，原因見下方「根因」。
>
> 另外補上初版完全沒寫的一段：**這道防護是為了回應一個 19:00:11 送達的審查警告才寫的——而它用警告點名的那個輸入去測試它。**

> ### 2026-11-18 晚間補充：測過了，沒有重現
>
> 同一天晚上用替身做了三種測試：`Remove-Item` 刪 8 MB、`cmd /c rd /s /q` 刪 8 MB、以及 `cmd /c rd /s /q` 刪 128 × 8 MB（1 GB）。在 26200.8457 與更新後的 26200.9974 各跑一輪：**快照每次都回原內容，0 個全零**。所以 TRIM、刪除 API、1 GB 規模都不是觸發點；VSS NULL 區塊仍是「最佳解釋、未證實」，不是已確認的原因。
>
> 兩個數字更正：**78 是下限**（實際至少 ~112 檔；15 檔全零）；**實際零化的是 8.5 MB**，144.9 MB 是受損檔的總大小（其中一個 134 MB 的檔只有幾個 4 KB 洞）。
>
> 重開機後 Windows 會重排 shadow 裝置編號（S22／S23 變成 `ShadowCopy1/2`），寫死的 `HarddiskVolumeShadowCopyNN` 不能跨重開機使用。

## 事件摘要

- **時間**：2026-11-16 傍晚，約 19:02–19:19（當地時間）。
- **背景**：agent 幫我寫了「安裝／卸載自製外掛」的一對腳本；卸載腳本有 `-Dest` 路徑參數與一組「安全防護」，我請 agent 測試防護有沒有用。
- **觸發**：測試值用了 `-Dest "C:\" -Force`。正規化函式**刻意不修剪長度 3 的磁碟根**（`C:\` 維持 `C:\`），而磁碟根檢查寫成 `^[A-Za-z]:$`，只認修剪後的 `C:`；`-Force` 又跳過資料夾名稱檢查。兩個各自正確的設計互相抵銷。
- **結果**：腳本執行 `cmd /c rd /s /q "C:\"`。指令 19:02:16 送出、19:04:23 中止，**上限 127 秒**；19:05:25 才確認 `C:\work` 只剩空殼。
- **復原（已修正）**：當天 13:16 的影子複本還在，`robocopy /E /COPYALL` 回報 143 目錄 / 1,372 檔案 / 1.744 GB / 0 FAILED——**但這只證明複製忠實，不證明內容正確**。2026-11-18 逐檔掃描發現 78 個以上檔案有零段、15 個全毀（實際零化 8.5 MB）。
- **真正失去的**：快照（13:16）到事發（19:02）之間新建的內容，**以及影子本身回傳 NULL 的那部分檔案內容**。
- **沒有損壞的**：系統目錄、使用者目錄、其他磁碟——**這是運氣**（ACL 與時序），不是安全設計。

## 根因

### 直接原因：路徑沒有正規化，就被餵給刪除動詞

```powershell
# 失敗鏈（真實版，取自事後復盤的原始碼）
function Get-Canonical([string]$p) {
  $full = [System.IO.Path]::GetFullPath($p)
  if ($full.Length -gt 3) { $full = $full.TrimEnd('\', '/') }   # ← A：長度 3 的磁碟根刻意不修剪
  return $full
}

$canon = Get-Canonical "C:\"            # → "C:\"（不是 "C:"）
if ($canon -match '^[A-Za-z]:$') { fail }   # ← B：只認修剪後的 "C:"
...
cmd /c rd /s /q "$canon"                # 刪除動詞直接吃這個路徑
```

問題不是「有沒有寫防護」，而是**兩道各自正確的設計互相抵銷**。A 的 `-gt 3` 是刻意的——作者知道磁碟根是 3 個字元，所以不把它修剪成 `C:`；B 的正則卻只認修剪後的 `C:`。合起來，`C:\` 兩邊都過。

同一份程式裡，**使用者目錄的比較其實是有效的**——測試時 `-Dest "<使用者目錄>\"` 確實被擋下。所以初版寫「`USERPROFILE` 比較永遠不成立」也是錯的：真正漏掉的是磁碟根。

這還牽出一個更難看的問題：**這道防護是為了回應 19:00:11 送達的審查警告才寫的**，而審查的 P0 第一條就點名了 `-Dest C:\`。防護寫好了，卻用那個被點名的輸入去驗證它。

### 為什麼沒有第二層擋住

| 防線 | 為什麼失效 |
|---|---|
| Agent 的授權／批准 | 會話開的是 full access：工具呼叫不逐次詢問。使用者授權的是「自動工作」，不是「可以無聲刪光」。 |
| Sandbox | 刪除是子行程（`cmd /c rd`）的副作用；full access 下不限制子行程。 |
| shell 工具的命令檢查 | 工具只看到 `pwsh -File uninstall.ps1 -Dest "C:\" -Force`；**刪除動詞在腳本檔案裡**，不在命令列上，字串比對抓不到。 |
| 腳本自己的防護 | 只覆蓋作者想到的情況；尾端分隔符、`-Force`、磁碟根都沒處理。 |
| Agent 的判斷 | 它選擇用真實磁碟根當測試值，而不是暫存目錄；也沒有人要求它先 dry-run、先列清單、先問人。 |
| 獨立審查 | **其實有效**：19:00:11 就送出 P0 警告，agent 也在 59 秒內照著改了。問題不在「有沒有警告」，在實作與驗證。 |
| 刪除前 checkpoint | 不存在。 |
| 備份 | 工作目錄沒有即時備份；唯一救命的是「剛好開著系統保護」。 |

### 我自己的責任

最該自責的一點：**我在真實資料路徑上測試「刪除保護」**。正確做法是在暫存目錄＋暫存 profile 上測試，或先讓 agent 產出「將刪除清單」再人工確認。防護函式是寫來測試的，我卻讓它的失敗直接作用在唯一的資料上。

## 為什麼 VSS 影子複本救了這件事

Windows 的磁碟區陰影複製服務（VSS，Volume Shadow Copy Service）會在背景對磁碟區做 copy-on-write 快照。快照只保存「被改寫的區塊」，所以佔用空間遠小於完整複本；我的系統保護設定上限約 9.5 GB，實際只用了一小部分。這次最新的影子複本在事故前約 6 小時，足以涵蓋全部既有檔案。

救援步驟（管理員 PowerShell；影子編號每次不同，以 `vssadmin` 輸出為準）：

```powershell
# 1) 列出所有影子複本
vssadmin list shadows /for=C:

# 2) 把最新的影子磁碟區掛成目錄連結（需要管理員）
#    把 HarddiskVolumeShadowCopyNN 換成上一步看到的編號
cmd /c mklink /d C:\restore "\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy23\"

# 3) 從影子複本把資料夾複製回來（不直接覆蓋，先複製到安全位置再比對）
robocopy "C:\restore\work" "C:\work" /E /COPYALL /R:1 /W:1

# 4) 核對數量與大小（必要，但不夠）
Get-ChildItem "C:\work" -Recurse -File | Measure-Object -Property Length -Sum
# 期望：1,372 個檔案、約 1.744 GB

# 5) 真正該做的：逐檔驗內容。頁級零段掃描（整頁 4096 位元組全零 = 可疑）
python scripts\scan-zero-damage.py "C:\work"
# 另可對關鍵檔抽樣雜湊、Office／zip 用 zipfile.testzip()

# 5) 確認無誤後移除連結（只是連結，不佔空間）
cmd /c rmdir C:\restore
```

核對結果：**143 目錄、1,372 檔案、1.744 GB、robocopy 0 FAILED**，兩側檔案數與位元組一致。

**但「一致」在這裡什麼都證明不了。** 兩天後逐檔掃描才發現：78 個以上檔案有零段，15 個全毀（實際零化 8.5 MB）。影子的檔案大小本來就是對的，所以任何「與影子核對一致」的結論都會通過。真正該問的是「內容對不對」，而我當時沒問。

這就是下一節要講的：**影子複本本身可能就是壞的。**

### 但要清楚 VSS 的極限

- **它會不報錯地回傳 NULL 區塊**：4 KB 叢集邊界、檔案大小不變、事件日誌沒有任何 VSS 錯誤。這是已被外部重複重現的 VSS 行為；261116 是否由它造成仍未證實。從 Windows 8.1 一路到 Windows 11 25H2 都有人重現——見 [`vss-null-blocks.md`](vss-null-blocks.md)。
- **它是快照，不是備份**：磁碟壞掉、被格式化、被加密，快照一起沒。
- **必須先有還原點**：系統保護沒開就沒有。消費級 Windows 不保證預設開啟；即使開了，`Checkpoint-Computer` 預設每 24 小時只能建一次。
- **只看得到快照時間點**：13:16 之後新建的檔案不在裡面。
- **需要管理員權限**才能掛載與讀取；不是一般使用者隨手能做的事。
- **會自動淘汰**：舊快照會因空間上限被覆蓋，放著不管會失去救命點。

這次能拿回檔案清單，是「系統保護剛好開著 + 快照剛好夠新 + 我有管理員權限 + 我知道 VSS 怎麼用」四個巧合疊起來。而要讓**內容**也回來，還多一個我當時完全不知道的條件：**影子本身沒有把那些區塊清成零**。這個條件沒有成立。

所以準確的說法是：**一半靠 VSS，一半靠運氣。** 這不是可依賴的防線。

## 給 AI agent 使用者的 5 個防護步驟

### 1. 開啟系統保護，並實際確認還原點存在

```powershell
# 確認系統保護狀態
Get-ComputerRestorePoint                     # 需要管理員
vssadmin list shadows /for=C:                # 看有幾個影子複本、時間多新
```

Windows：`控制台 → 系統 → 系統保護 → 設定 → 開啟系統保護`，並按「立即建立」一次。macOS 開啟 Time Machine 的本機快照；Linux 用 btrfs／LVM 快照或 Timeshift／Snapper。**沒有驗證過還原點，就等於沒有還原點。**

### 2. 工作資料一定要有外接或雲端備份（3-2-1）

AI agent 刪得掉本機任何你有權限的東西，包含你的備份資料夾。至少一份要在另一顆實體碟或雲端，且要有版本歷史。定期（例如每月）實際還原一次小樣本，確認備份真的能用。

### 3. 不要給 agent 管理員權限；full access 只短暫開啟

- 平常跑在 `workspace-write`（或唯讀）模式，需要時才提升。
- 用**標準使用者帳號**跑 agent，不要用管理員帳號；這樣即使誤刪，作業系統會擋住系統目錄。
- full access 留給「明確知道要幹嘛」的短會話，結束就收回。
- 高風險測試（安裝／卸載／清理腳本）在虛擬機或獨立測試帳號裡做。

### 4. 破壞性操作先 dry-run、先看清單

在按下「刪除」之前，要求 agent：

- 先列出「將刪除的路徑、檔案數、總大小」，不要直接執行；
- 用 `-WhatIf`（PowerShell）或先複製到暫存目錄再操作；
- 一次只刪一個明確目標，不要「刪整個資料夾」；
- 你逐項看過清單才放行。

```powershell
# 好習慣：先看，不刪
Get-ChildItem "C:\work\test-target" -Recurse -File |
    Measure-Object -Property Length -Sum    # 檔案數與大小
```

### 5. 把守則寫進 agent 的全域指令檔

在 `AGENTS.md`（或同等全域指令）加入類似內容，讓每個會話都遵守：

```markdown
## 高危操作守則

- 任何刪除／大量覆寫指令，執行前必須 canonicalize 路徑
  （GetFullPath 加上去掉尾端分隔符），並拒絕：
  磁碟根、使用者目錄、.dsh、腳本自身目錄、workspace 以外的路徑。
- 不可把使用者輸入或命令列參數直接餵給
  Remove-Item -Recurse、rd /s /q、robocopy /MIR、rm -rf。
- 這類腳本只在暫存目錄＋暫存 profile 測試，不得用真實資料測試。
- 刪除前先列出清單；不確定就停下來問人。
```

## 給 agent 開發者的 3 個建議

### 1. 路徑防護要做在工具層，而且要 deterministic

不要依賴「模型會自己寫對防護」——這次事故就是模型寫的防護被模型自己繞過。工具層應在執行前做 canonicalize、解析 junction／symlink、套用保護清單，並對「磁碟根、使用者目錄、agent 自身資料、workspace 外」的破壞性呼叫要求人工批准（即使 full access 也一樣）。路徑比較要處理尾端分隔符、`C:` 磁碟相對路徑、UNC、`\\?\` 裝置路徑、8.3 短名與大小寫。

### 2. 測試一律用暫存目錄與暫存 profile

任何「刪除／覆寫」類腳本，測試資料只能在 `%TEMP%` 或專用測試帳號裡產生。這一點應該寫進 agent 的行為指引，並在工具描述層提醒；如果腳本帶有 `-Dest`、`-Path`、`--target` 這類參數，執行前的批准卡片要顯示 canonical 目標，讓「`C:\`」這種值一眼被看到。

**更關鍵的一條：測試輸入必須是替身，不能是被保護的目標本身。** 要驗證「`C:\` 會被擋」，應該跑 `-Dest "C:\__probe_does_not_exist__"`——守門失效也只會刪掉一個不存在的東西。用 `-Dest "C:\"` 去驗證守門，等於把安全測試和使用者資料綁在同一個物件上；守門一旦有洞，測試就變成事故。

### 3. 失敗即停，並提供破壞性操作的復原路徑

- 參數看起來像磁碟根、使用者目錄或 workspace 外時，**停止並回報**，不要「測試看看會不會被擋」。
- 刪除前建立 checkpoint／quarantine（例如搬到 `.trash` 並保留 N 天），UI 明確顯示「已建立還原點」。
- 提供結構化審計記錄（目標、檔案數、時間、批准來源）與一鍵 undo。
- 現有機制（例如「自動授權審查」：每次工具呼叫前由模型對照使用者要求檢查、越界就等批准）應該預設開啟，或至少成為破壞性操作的最低標；本案例中該機制並未啟用。
- 命令列看不到被呼叫腳本裡有什麼時，把「執行這個腳本」當成高風險動作處理，而不是當成普通指令。

## 教訓

1. **不可逆的操作必須有第二雙眼睛。** 不是因為 AI 不可靠，而是因為人與 AI 都會犯錯；第二道關卡的作用是讓「一個錯誤」不足以變成「資料全毀」。
2. **防護函式不是萬能。** 你想到的邊界（空字串、使用者目錄）永遠少於真實世界的邊界（尾端分隔符、`-Force`、junction、大小寫）。正規化與保護清單應該由工具層負責。
3. **備份是唯一的保險。** 快照、VSS、Time Machine 都是「可能有用」；只有真的驗證過的備份才是「一定有用」。而 3-2-1 備份要放在 agent 刪不到的地方。
4. **full access 的流暢度是用風險換來的。** 它適合有明確範圍的任務；不適合「幫我測一下這個會刪東西的腳本」。
5. **測試必須隔離。** 用真實資料路徑測試刪除保護，等於用唯一一份資料做實驗。
6. **事後追查需要記錄。** 這次因為有 VSS 才不需要追查；如果沒有，連「刪了什麼」都拼不回來。工具應該留下結構化日誌。
7. **成本對比很懸殊。** 一次事故的救援時間（掛載影子、robocopy、逐項核對）遠超過事先做一次 dry-run、建一個暫存目錄或等一個批准提示。
8. **「與影子一致」不是驗收。** 影子本身可能就是零，而且不會報錯。驗收要驗內容：頁級零段掃描、雜湊、Office／zip 用 `testzip()`。而且**先把影子複製到另一顆碟再驗**——直接還原會把 live 上的區塊原位蓋掉，之後想回答「原檔到底壞了沒有」就永遠沒有證據。
9. **警告送到，不等於被處理。** 這次的獨立審查在致命指令前 **2 分 5 秒**送達，agent 也在 **59 秒內**照著改；還是出事。因為它的驗證方式是「拿被保護的目標本身當測試輸入」。檢查這一件事，比檢查有沒有警告更有用。
10. **「指令逾時被移到背景」是危險訊號。** 這次的破壞指令之所以跑滿 120 秒，正是因為它已經開始刪東西。看到逾時，先假設它做了事，不要假設它卡住了。

## 給讀者的 60 秒檢查清單

- [ ] 系統保護／快照有開，而且我實際看過（管理員）`vssadmin list shadows` 有東西。
- [ ] 重要工作資料有外接或雲端備份，並且還原過一次。
- [ ] agent 平常不用管理員帳號，full access 不長期開著。
- [ ] 破壞性操作一律先 dry-run、先看清單。
- [ ] 全域 agent 指令檔有高危操作守則。
- [ ] 我知道我的「還原點」是什麼、怎麼用、多新。
